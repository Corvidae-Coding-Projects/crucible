# ADR-0004: Linux local execution and immutable run-evidence boundaries

- **Status:** Accepted
- **Date:** 2026-08-13
- **Decision owners:** dollspace.gay (approved 2026-08-13)
- **Related issue:** Phase 1 `crucible run` breadth slice
- **Supersedes:** None
- **Amends:** ADR-0001 (schema version 3 and run persistence)

## Context and evidence

Phase 1 requires Crucible to execute a CLI target without a shell, apply bounded controls, capture
stdout and stderr without deadlock, terminate the process tree at timeout, distinguish target facts
from harness failures, and persist immutable raw evidence. The pinned Verus toolchain cannot specify
the operating-system process, descriptor, pipe, thread, clock, signal, bubblewrap, prlimit, or
SQLite operations needed to perform those effects.

The first operational adapter is intentionally platform-specific: Linux with bubblewrap and
prlimit. This is a breadth step toward the complete set of adapters in the specification, not a
redefinition of supported scope. Other host adapters remain required and fail closed until their
controls and evidence mappings are implemented.

## Decision

Add `crucible run <configuration>` with a verified execution-facing configuration projection and
verified local execution plan. Before target preparation, the Linux host adapter hashes the current
Crucible harness, bubblewrap, and prlimit binaries and runs an executable probe of the same
bubblewrap-prlimit stack used for execution. It publishes an enforcement manifest only after the
probe report is authenticated by verified code. The adapter then opens the selected target without
following symlinks, authenticates and materializes the selected bytes, places bubblewrap in a
dedicated process group, applies prlimit inside the namespaces, and invokes a small Crucible
supervisor with a verified canonical direct-argument wire. The wire enters over supervisor stdin;
the target receives null stdin and never receives a host-backed control mount. The supervisor spawns
the target without a shell and emits nonce-bound start and termination records on a write-only stream
that the target cannot read. The adapter removes those authenticated records before persisting exact
target output. Before target spawn, the supervisor marks itself non-dumpable; the target namespace
exposes no procfs and drops all capabilities, so the target cannot read the supervisor's nonce even
under a permissive host ptrace policy. The adapter uses a private working directory and cleared
environment and captures both output streams concurrently. Each stream is retained only to its
configured cap while the adapter continues to drain and count discarded bytes; timeout or execution
failure kills and waits for the process group.

Add SQLite schema version 3 for target-build manifests, capability manifests, runs, attempts,
effective controls, observations, and harness failures. Generated bytes are published to the
content-addressed store before an immediate, full-synchronous SQLite transaction references them.
Attempt transitions and evidence rows are conditional and insert-only. Target completion and
termination remain raw facts; the adapter does not turn a nonzero exit or timeout into a finding.

Use three registered external bodies: `CLI-HOST-LOCAL-SUPERVISOR-001` for the private direct-argv
supervisor, `CLI-HOST-LOCAL-RUN-001` for capability probing, target preparation, execution, capture,
and cleanup, and `CLI-HOST-RUN-STORE-001` for run identity allocation and durable evidence
transitions.

## Preserved invariants

- Target command and argument bytes are passed directly; no shell parses them.
- Requested controls, executable probe evidence, effective values, enforcement mechanisms, target
  bytes, harness/tool artifacts, runtime versions, and configuration identity are retained
  independently.
- Wrapper/setup failures cannot be reclassified as target outcomes: a target outcome requires an
  authenticated supervisor start marker and an exit/signal marker consistent with wrapper status.
- The target has no writable host-backed control path or readable status/nonce channel. It cannot
  traverse procfs to reopen supervisor descriptors or trace the non-dumpable supervisor.
- Output caps bound retention, not pipe draining; discarded byte counts remain exact.
- Timeout and error cleanup kill and wait for the configured process group.
- Target outcomes and harness failures are disjoint persisted states.
- An observation references already-published immutable artifacts and is inserted at most once.
- Existing schema versions migrate monotonically; historical rows are not rewritten.
- The Linux-first adapter does not remove the required Windows and later platform backends.

## Alternatives considered

- A shell wrapper would make argument meaning host-dependent and introduce injection behavior.
- Binding the host root read-only into the sandbox would expose unrelated host files and make the
  effective isolation weaker than the recorded capability.
- Stopping reads when retention fills can deadlock a target blocked on a full pipe.
- Recording only a verdict would erase raw termination and output evidence needed by later oracles.
- Reserving identities in process memory would collide across concurrent invocations and restarts.

## Verus and trusted-boundary impact

The execution projection, plan admission, canonical argument wire, capability-report authentication,
exact capability and target-manifest bytes, wrapper/target evidence classification, output
accounting, portable observation construction, run-state admission, and schema policy are Verus Rust
with executable-to-spec contracts. The three host bodies are explicit trusted boundaries because
the current toolchain does not verify the effectful dependencies. Their complete assumptions,
risks, mitigations, test references, and exact source bindings are recorded in `tcb/ledger.tsv` and
`tcb/approved.tsv`.

The boundary is not evidence that bubblewrap, prlimit, Linux, Rust standard-library process APIs,
rustix, rusqlite, or SQLite are proved. Those dependencies can violate the returned evidence. The
adapter therefore performs descriptor checks, exact byte authentication, explicit plan mapping,
conditional persistence transitions, and process-level tests outside the proof.

## Safety, privacy, resource, and authorization impact

Crucible is a general-purpose software testing and bug-reduction system. These controls limit the
effects of buggy or resource-hungry test subjects and make results reproducible; they do not redefine
the product as a cybersecurity tool.

The default Linux plan unshares all supported namespaces, does not share the host network, exposes
only read-only runtime and target paths, clears inherited environment variables, omits procfs, drops
all capabilities, provides private `/tmp` and `/work`, and applies address-space, process-count,
file-size, wall-time, and retained-output controls. A configuration that requests a required
capability absent from the adapter fails before target execution. Target output remains untrusted
bounded artifact content.

The command reads the selected configuration and target, writes only within the selected
`.crucible` workspace plus an internal temporary executable, and performs no Crucible-controlled
network request.

## Compatibility and migration

Fresh workspaces use schema version 3. Exact version-1 and version-2 workspaces migrate through the
new run migration in one transaction. Unknown, divergent, or partially applied histories are
rejected. Raw observation bytes, capability manifests, target-build manifests, and effective
controls carry identities independent of the SQLite schema version.

The initial adapter accepts the documented local `.crucible` storage root on Linux. Additional
storage and host adapters must preserve the same raw evidence meanings and add their own capability
identities rather than coercing results into the Linux representation.

## Verification and acceptance

Before publication:

- runtime plan tests must prove exact projection of controls and rejection of unsupported required
  capabilities;
- Verus proof fixtures must check plan/configuration and local-evidence/observation contracts;
- process tests must execute a direct nonzero exit, kill a tagged descendant at timeout, retain and
  discard output at the exact boundary while continuing to drain, and persist target-preparation
  failure without an observation; they must also prove that the target cannot reach a host-backed
  supervisor control path or a supervisor descriptor through procfs, and that a native ptrace
  attempt against the supervisor is denied;
- schema tests must authenticate the version-3 migration and exact database shape;
- formatting, Clippy, workspace tests, Verus verification, and strict trusted-boundary
  reconciliation must pass with no Rust `allow` attributes.

## Consequences and follow-up

Crucible gains its first end-to-end target execution and immutable observation path. It also gains
a material trusted surface whose behavior must remain visible in capability manifests and audited
on every dependency or platform-policy change.

The next breadth slice is read-only inspection of persisted runs and observations, followed by hard
oracles, findings and deduplication, replay, corpus ingestion and mutation, minimization, and
portable bundles. Cancellation cleanup, other input-delivery modes, additional host backends,
executor proof identity, stronger crash consistency, and deeper formal correspondence remain
required follow-up work; none is removed from the specification.
